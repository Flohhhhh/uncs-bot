# WARDOGS compatibility review

The dashboard adapter was initially checked against the public official RCON client and published 0.1.2 patch notes on September 30, 2026, with the latest public-source recheck on October 2. No production credentials or game mutations were used for the public-source review.

The October 2 recheck found a newer [official security and stability hotfix notice](https://steamcommunity.com/app/1867240/announcements/), posted October 1 and scheduled for October 2 at 08:00 UTC with an estimated one-hour outage. It does not list new RCON routes or configuration keys, and the notice alone does not prove completion or installation on The UNCs server. Version 0.1.2 remains the latest detailed settings changelog on that page.

The [public standalone template](http://rcon.wardogs.com/ServerSettings.ini) still returned HTTP 200 (4,151 bytes) on October 2: its 15 ordinary scalar controls match `src/common/server-settings.ts`; reserved IDs, banned IDs and rotation entries have dedicated management paths. The remaining template section contains RCON enable/bind/port/password/hash settings, which remain host-managed. It still supplies no verified description, daily-restart-time or AllowedHosts key. The UTF-8 template SHA-256 was `a2a660fc042e333debee7418166b4d38272ed71f98db46af2f2779424c9976b4`; its Last-Modified header, like the public API client, was September 14. Public console assets can lag a game hotfix. This inventory does not prove the running game's configuration or build, and a live ban result does not establish how the host persists startup ban entries.

## Verified sources

- [Official 0.1.2 announcement](https://steamcommunity.com/app/1867240/announcements/) (displayed 29 September): daily restart time in UTC, RCON AllowedHosts, capped player messages and broadcasts, Standard response detail by default, and reduced config internals.
- [Official API client](http://rcon.wardogs.com/js/api.js) and [official config parser](http://rcon.wardogs.com/js/config-doc.js), fetched on 30 September: reserved-player updates use the config document with `If-Match`; the console serializes arrays as `!Key=ClearArray` followed by `.Key=value`; map-specific experience and zone-layout catalogs are available when advertised by the server.
- [Official console markup](http://rcon.wardogs.com/app.html), fetched on 30 September: both broadcast and whisper inputs have a 200-character limit. This dashboard retains that conservative limit for both. It does not silently truncate messages.
- [Warcon author's updated protocol observations](https://github.com/warcon-app/warcon/blob/main/docs/wardogs-api.md), read from [current raw source](https://raw.githubusercontent.com/warcon-app/warcon/main/docs/wardogs-api.md): a separate CL-507060 server inspected on 30 September still advertised 29 routes, accepted 256-character broadcasts and rejected 257, rejected offline bans with `player_not_found`, and omitted validation `timingsMs`. These are observations of that server, not verification of The UNCs production build.

## Implemented behavior

- Discover supported mutation routes from `/v1/capabilities`. Do not infer new routes from a version label or force the server into Full response detail.
- Prefer advertised live whitelist routes. Otherwise edit only `DefaultReservedPlayerIds` in the configuration, preserving unrelated values, existing access, held-back slot settings, the server feed and credentials. Recognize Unreal's clear, append, unique append, remove and scalar array operations. Explicitly clear the array when its last member is removed.
- Refuse visibly redacted documents, read-only or pinned whitelist keys, malformed documents and ambiguous whitelist sections. Use advertised validation when available, enforce the advertised request body limit, and submit with the revision in `If-Match`. Never use `force` or `fullApply`.
- Confirm every whitelist mutation against the running reserved-player list. Report **applied** immediately when the requested live state is present. Otherwise report pending or unknown; do not claim a restart is always required. The owner has reported successful live additions through the current official RCON tool.
- Confirm ban changes against the running ban list. Explain an offline-player refusal without falling back to an unrequested config rewrite. Game bans are currently permanent; this dashboard does not invent game-native expiry or queue tiers.
- Validate selected maps, lighting, experiences and zone layouts against current catalogs. Check map-specific experience compatibility when that route exists.
- Do not depend on internal timing fields. Reject boolean or array conflict results and explicit upstream refusals. Do not return raw upstream error text or configuration documents to browsers.
- Never retry mutations automatically. A lost response is unknown and requires checking server state. Honor `Retry-After` before subsequent requests.

## Deployment verification limits

Public patch notes do not document every redaction format or the `AllowedHosts` syntax. Configure network restrictions through the host using its verified instructions; this dashboard does not change them. Daily process-restart scheduling remains a host setting, distinct from the dashboard's match restart action.

Preserve the existing production whitelist. The owner approved replacing the old xREALM feed destination with Gramps; that connection is configured but first native delivery remains unverified. Do not change feed settings during testing or assume another tool's receiver is required for RCON. No planned queue tiers, seeding expiry or paid-access rules are activated by this adapter.

## Team changes and preferences

The current [official client](http://rcon.wardogs.com/js/api.js) sends a faction **name** from the live status to `PATCH /v1/players/{steamId}`. Player rows use `RED`, `BLU` and `GRN` codes. The [official palette](http://rcon.wardogs.com/js/config.js) maps these to `#D86060`, `#5B95D8` and `#7BC462`; [the official interface](http://rcon.wardogs.com/js/app.js) resolves the current names using those exact colors. Its demonstration data names Blue as Lonestar, Red as Valkyra and Green as Manticore. The dashboard still obtains destinations from the connected server, rather than treating sample names as a guarantee.

The adapter checks the chosen live faction and connected player before sending a move, avoids a redundant move if the assignment is already correct, and checks fresh status and player data afterward. A confirmed assignment is reported separately from an unconfirmed or still-pending move. A faction assignment does not prove that an existing living character has respawned on its new side.

The official client follows its team PATCH with a separate kill request. This dashboard does **not** kill players automatically; it states that respawn may still be needed. Staff can use the separately authorized kill action when appropriate. No automatic team enforcement or join-time preference is enabled.

The reviewed public API and [official configuration editor](http://rcon.wardogs.com/js/config-editor.js) do not expose a per-player or Discord-role preferred-faction setting. They expose only the general `bLockOverpopulatedTeamsConfig` and `OverpopulatedTeamThresholdConfig` controls under `WDGameStateSession`. These balance controls are not UNC membership preferences. A persistent group preference would require separately designed identity linkage and automation, with an explicit policy about consent, population balance, repeat moves and respawn. Current production behavior has not been tested by moving anyone.

The [official demonstration fixture](http://rcon.wardogs.com/js/test-data.js), rechecked October 1, includes a player with `steamId: null`. This is not evidence that The UNCs live server returns such records. The roster adapter now accepts that documented shape, excludes it from actionable rows and reports an explicit unlinked count. Staff see that player controls and team counts exclude those entries; the game's total population remains unchanged. It never manufactures an ID or targets by display name. Team preflight/readback still locate the explicitly selected SteamID. Other malformed identity shapes remain rejected.

## October 1 research: optional events, ballots and scheduling

The owner's choice remains **optional 50v50**, not a replacement for normal play. [Reddit's recent discussion](https://www.reddit.com/r/WarDogs/comments/1wsltsc/50v50_community_servers_are_surprisingly_fun/) contains both enthusiasm for larger fights and reports of severe one-sided matches. It establishes player interest and tradeoffs, not an official game mode, better retention or verified progression rules.

The [WarDogs Server Commands author's changelog](https://wardogsbot.com/updates), reviewed October 1, documents a working community approach: exclude one of three teams, warn affected players, assign arrivals to the remaining teams, optionally enforce a population limit and restrict balancing to an early-round window. It reports that the game's population lock can conflict with an excluded team and needs restoration afterward. Recent entries describe restart-persistent assignments, permitting switches that improve balance, and an observation-only option. These are the author's implementation reports, not an independent test or proof of the UNCs server's behavior. Their existence does not require installing that bot or granting it our credentials.

Recommended UNCs event choices:

| Event                      | Mechanism already available in this dashboard                                                   | Additional work before advertising it                                                                                              |
| -------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Infantry night             | Select a map's advertised infantry experience; queue its rotation entry                         | Rehearse that exact map/mode combination and restore the usual rotation afterward                                                  |
| Hardcore night             | Select a hardcore experience if the map advertises one                                          | Explain the chosen rules and confirm compatibility; do not infer a damage multiplier                                               |
| Dusk/fog rotation          | Choose advertised lighting for each map                                                         | Preview readability and retain an easy return to the regular rotation                                                              |
| New-player/seeding evening | Staff guidance and spaced welcomes                                                              | Publish a time and clear expectations; no automatic reward promises                                                                |
| Community map night        | Durable Discord ballots can queue a validated winning map without ending the current round      | Controlled Discord/game acceptance; draft #69's new mode/reminder controls additionally need their human-owned migration           |
| 50v50 event                | Optional event page, selected teams, warnings, durable operations and stop/restoration controls | Verified round timing and controlled warning/balance/recovery acceptance; original event tables already have a committed migration |
| Friend-group scrim         | Staff can review a SteamID-based batch team move                                                | Opt-in verified Discord/Steam linkage and group planning; automatic voice-channel sorting remains research-only                    |

These are event formats, not claims of new native modes. Cash/level settings are joining restrictions, not grants of starting money or XP. Do not advertise pistols-only, vehicle spawn limits, team tickets, custom damage or 150-player modes without a supported setting and host capacity evidence.

Optional 50v50 controls and automatic map ballots are deployed but remain off. They retain explicit server targeting, reviewed choices, durable receipts and stop/override behavior. See [operating behavior and remaining verification](SERVER_COMMUNITY.md). Draft [#69](https://github.com/Flohhhhh/uncs-bot/pull/69) adds saved map/mode switches and score reminders; its distinct migration is still human-owned. No live activation, verified next-round adoption or purchase-free window is claimed. Discord-based friend-group assignment remains research-only.

The other bot's [map-vote documentation](https://docs.wardogsbot.com/map-votes) uses Discord buttons and sets the winning next map. That is evidence for an external community ballot, not a game-native chat-voting endpoint. Gramps ballots retain a server and eligible map/mode snapshot, one current vote per authenticated Discord account, a closing rule and one recorded close operation. Ties or no votes retain the rotation. Queueing revalidates the map, creator access, connection, position and configuration revision; a winner is not “queued” until its saved next position is confirmed. Discord voting does not verify an active game player or Steam ownership. Draft #69's score reminders follow the separately documented 100-point policy and remain off pending acceptance.

The author's [schedule documentation](https://docs.wardogsbot.com/schedules) lists **restart match**, end match, maps, lighting and announcements. A final public-source check found xREALM's [documented match-end restart task](https://www.xrealm.com/en/blog/wardogs-server-restart-after-match-end). This resolves the earlier uncertainty about host support; no public scheduler API was established. See [owner setup and limits](SERVER_COMMUNITY.md#host-restart-schedules). Native uptime timing differs between the provider's English and [Polish guide](https://xrealm.com/pl/blog/wardogs-restart-serwera-po-zakonczeniu-meczu), so do not promise a build-specific interval without verification. No host schedule, command, Discord message or game action was activated by this research.

## October 1 research: East versus Central

**Recommendation: favor East for an evening-focused community if actual hosting location and player latency support it. Keep the live server unchanged pending those checks.** This is an inference from two independent public sources, not a measured lift for The UNCs.

[WardogServers' zone history](https://wardogservers.com/stats), observed at its 08:11 UTC October 1 update, reported:

| Eastern time, Sep 30–Oct 1 | NA East players | NA Central players |
| -------------------------- | --------------: | -----------------: |
| 8:03 pm                    |          40,403 |             30,121 |
| 9:03 pm                    |          46,903 |             36,020 |
| 11:03 pm                   |          38,512 |             38,047 |
| 12:07 am                   |          26,745 |             30,671 |

These include official and community servers. East led during the evening; Central led after midnight in this sample. Use its **zones**, because the site's grouped East region also includes NA North. This is one day's observational sample with collection gaps, not a representative experiment or unique-visitor count.

[BattleMetrics' community-only ranking](https://www.battlemetrics.com/servers/wardogs?features%5B9c32a41e-afaf-11f1-a8ce-0f73df60e974%5D=false) was inspected in the browser October 1 around 08:30 UTC. The first twenty community entries contained eight NA East, three NA West and no NA Central servers. Examples included [Old Guys 2, overall rank #63](https://www.battlemetrics.com/servers/wardogs/41277569), [7th Ranger Regiment, #157](https://www.battlemetrics.com/servers/wardogs/41279886), [TEG NA#2, #208](https://www.battlemetrics.com/servers/wardogs/41277720), and [TEG NA#1, #273](https://www.battlemetrics.com/servers/wardogs/41281872). These are overall displayed ranks after filtering out official servers, not region-specific ranks. Established communities and multiple servers from the same community are represented, so this is supporting evidence, not twenty independent comparisons. The inspected detail page's historical graphs returned no data; no seven-day retention or population-average claim is supported. Server names advertising boosts do not verify a current game bonus.

The [xREALM joining guide](https://xrealm.com/en/blog/how-to-connect-to-your-wardogs-server) tells players to select the region where the server is hosted. No supported cosmetic East/Central override was found in the reviewed configuration surface. Verify the actual host region with its owner; changing the displayed name alone is not evidence of changing discovery region or improving latency. Before a relocation, compare equivalent community modes/capacities across several weekday and weekend evening windows, record time to seed and player-hours, and obtain representative player latency. Rankings and a current full-server count cannot establish which region causes better retention.

## October 1 research only: Discord groups and round-start teams

The owner explicitly requested **feasibility research, not implementation**. No voice listener, automatic team assignment, new Discord permissions or production action was added.

The pieces exist in principle: Discord sends [voice-state events](https://docs.discord.com/developers/events/gateway-events#voice-state-update) when users join, leave or move channels; the [Guild Voice States intent](https://docs.discord.com/developers/events/gateway#gateway-intents) enables them. Gramps currently requests only Guilds and GuildMembers, so it does not yet subscribe. Membership observation does not require listening to or recording audio. WARDOGS' team-move and respawn behavior is described above.

A sensible future flow is opt-in: link and verify a Steam account, join a designated team/group voice channel, show the planned game server and team, warn before purchases, then freeze the group snapshot for one round-start assignment. A Blue channel could request Blue; other friend-group channels could be kept together and allocated to opposing teams. A neutral lobby, bots, unlinked identities and people on another game server must be excluded. A channel change during a round should affect the next round, not repeatedly move the player. Team membership does not create an in-game squad or guarantee seats for an oversized group.

The current whitelist application records Discord identity and a **self-reported** SteamID, with `steamOwnershipVerified=false`; approval alone does not prove Steam ownership. Do not reuse that claim as authority to move someone else's game character. Verified linkage, withdrawal of consent, stale/reconnected voice state and visibility of the allowed channels need explicit handling.

Round timing is the main unresolved game limitation. The existing worker infers transitions from snapshots and may detect them after loading or miss a same-map reset. No reliable pre-purchase round-start event was verified. The official console performs a kill after a team switch; automatically reproducing that can cost a player purchased gear. Do not promise loss-free automatic assignment without a controlled test and a verified timing/respawn policy. A staff-reviewed assignment preview is a possible first release if automation remains unreliable.

Balance must treat each friend group as a unit and respect current teams, locks and capacity. If a group will not fit, keep it waiting or ask for a different team; do not silently split it, eject public players or disable balance restrictions. In a 50v50 event the selected event teams must govern assignment, so a fixed Blue preference cannot fight another balancer. Each round/server needs one recorded assignment plan and per-player outcomes; unknown moves must be inspected rather than replayed. The design remains suitable for later review, not enabled functionality.
