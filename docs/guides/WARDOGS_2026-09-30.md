# Wardogs compatibility review — 30 September 2026

The dashboard adapter was checked against the public official RCON client and the latest published 0.1.2 patch notes on 30 September 2026. No production server credentials or production mutations were used for this review.

## Verified sources

- [Official 0.1.2 announcement](https://steamcommunity.com/app/1867240/announcements/) (top announcement, displayed 29 September): daily restart time in UTC, RCON AllowedHosts, capped player messages and broadcasts, Standard response detail by default, and reduced config internals.
- [Official API client](http://rcon.wardogs.com/js/api.js) and [official config parser](http://rcon.wardogs.com/js/config-doc.js), fetched on 30 September: reserved-player updates use the config document with `If-Match`; the console serializes arrays as `!Key=ClearArray` followed by `.Key=value`; map-specific experience and zone-layout catalogs are available when advertised by the server.
- [Official console markup](http://rcon.wardogs.com/app.html), fetched on 30 September: both broadcast and whisper inputs have a 200-character limit. This dashboard retains that conservative limit for both. It does not silently truncate messages.
- [Warcon author's updated protocol observations](https://github.com/warcon-app/warcon/blob/main/docs/wardogs-api.md), read from [current raw source](https://raw.githubusercontent.com/warcon-app/warcon/main/docs/wardogs-api.md): a separate CL-507060 server inspected on 30 September still advertised 29 routes, accepted 256-character broadcasts and rejected 257, rejected offline bans with `player_not_found`, and omitted validation `timingsMs`. These are observations of that server, not verification of The UNCs production build.

## Implemented behavior

- Discover supported mutation routes from `/v1/capabilities`. Do not infer new routes from a version label or force the server into Full response detail.
- Prefer advertised live whitelist routes. Otherwise edit only `DefaultReservedPlayerIds` in the configuration, preserving unrelated values, existing access, held-back slot settings, the server feed and credentials. Recognize Unreal's clear, append, unique append, remove and scalar array operations. Explicitly clear the array when its last member is removed.
- Refuse visibly redacted documents, read-only or pinned whitelist keys, malformed documents and ambiguous whitelist sections. Use advertised validation when available, enforce the advertised request body limit, and submit with the revision in `If-Match`. Never use `force` or `fullApply`.
- Confirm every whitelist mutation against the running reserved-player list. Report **applied** immediately when the requested live state is present. Otherwise report pending or unknown; do not claim a restart is always required. The owner has reported successful live additions through the current official RCON tool.
- Confirm ban changes against the running ban list. Explain an offline-player refusal without falling back to an unrequested config rewrite. Game bans are currently permanent; this dashboard does not invent game-native expiry or queue tiers.
- Validate selected maps, lighting, experiences and zone layouts against current catalogs. Check map-specific experience compatibility when that route exists.
- Do not depend on internal timing fields. Reject boolean or array conflict results and explicit upstream refusals. Do not return raw upstream error text or configuration documents to browsers.
- Never retry mutations automatically. A lost response is unknown and requires checking server state. Honor `Retry-After` before subsequent requests.

## Still requires deployment verification

The actual production capabilities, server build, config visibility, network access rules and player list shape must be checked when connecting the dashboard. Public patch notes do not document every redaction format or the `AllowedHosts` syntax. Configure network restrictions through the host using its verified instructions; this dashboard does not change them. Daily process-restart scheduling remains a host setting, distinct from the dashboard's match restart action.

The existing production whitelist and feed destination must remain intact. No planned queue tiers, seeding expiry or paid-access rules are activated by this adapter.

## Team changes and preferences

The current [official client](http://rcon.wardogs.com/js/api.js) sends a faction **name** from the live status to `PATCH /v1/players/{steamId}`. Player rows use `RED`, `BLU` and `GRN` codes. The [official palette](http://rcon.wardogs.com/js/config.js) maps these to `#D86060`, `#5B95D8` and `#7BC462`; [the official interface](http://rcon.wardogs.com/js/app.js) resolves the current names using those exact colors. Its demonstration data names Blue as Lonestar, Red as Valkyra and Green as Manticore. The dashboard still obtains destinations from the connected server, rather than treating sample names as a guarantee.

The adapter checks the chosen live faction and connected player before sending a move, avoids a redundant move if the assignment is already correct, and checks fresh status and player data afterward. A confirmed assignment is reported separately from an unconfirmed or still-pending move. A faction assignment does not prove that an existing living character has respawned on its new side.

The official client follows its team PATCH with a separate kill request. This dashboard does **not** kill players automatically; it states that respawn may still be needed. Staff can use the separately authorized kill action when appropriate. No automatic team enforcement or join-time preference is enabled.

The reviewed public API and [official configuration editor](http://rcon.wardogs.com/js/config-editor.js) do not expose a per-player or Discord-role preferred-faction setting. They expose only the general `bLockOverpopulatedTeamsConfig` and `OverpopulatedTeamThresholdConfig` controls under `WDGameStateSession`. These balance controls are not UNC membership preferences. A persistent group preference would require separately designed identity linkage and automation, with an explicit policy about consent, population balance, repeat moves and respawn. Current production behavior has not been tested by moving anyone.

The [official demonstration fixture](http://rcon.wardogs.com/js/test-data.js) includes a player with `steamId: null`. This is not evidence that The UNCs live server returns such records. Team preflight and readback safely ignore unlinked identities when locating the explicitly selected SteamID. The existing overview schema still expects every displayed player to have a valid SteamID64; a real unlinked record would currently make that overview unavailable. Verify the live shape before expanding identity handling.
